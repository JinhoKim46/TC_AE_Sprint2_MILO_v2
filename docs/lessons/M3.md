# M3 lesson: tools, and the loop from a tool call to the answer

## Context

Without tools the bot can only talk. With tools it can record what the owner said, estimate an effect, and draft a
diagnosis card. The risk is that the model does these things carelessly, or invents the numbers they produce. M3 puts
the work in code and measures how well the model chooses.

## What was built

- **Six tools** with JSON schemas and risk tiers (`data/tools.yaml`, loaded by `src/milo/tools.py`):
  - `search_knowledge` (read), `get_recorded_facts` (read), `estimate_effect` (read),
  - `record_fact` (write), `draft_diagnosis` (write),
  - `reset_diagnosis` (destructive, needs approval).
- **Argument checks** before any handler runs: unknown tools, unknown fields, wrong types and values outside the enum
  return a typed error to the model. The model never reaches a handler with a bad argument.
- **Facts with status**: each fact keeps its value, unit, status (reported, conflicting or unknown) and evidence text.
  Unknown facts do not feed the estimate.
- **The estimate is computed in code**: `events × (baseline − new minutes) ÷ 60`, shown as a central value and a
  0.8× to 1.2× range. An input the owner did not give is labelled as assumed (the baseline and the new minutes). An
  event count the owner did not give is not assumed: the tool returns `needs_input`, and the bot must ask.
- **The tool loop** (`src/milo/app.py`): up to four model steps. Each tool call runs with the user id given to `ask`,
  never an id the model wrote. A destructive call is not run; the answer stops and asks for approval. Every call is
  recorded in `tool_results` with its policy decision.
- **Adapter** (`src/milo/llm.py`): tool specs go to the model in function-calling form; tool calls and results are
  converted to LangChain messages with their ids.
- **Tool evaluation** (`scripts/eval_tools.py`): 20 cases, scored on tool selection, parameters, and over-eager calls on
  the cases that need no tool.

## Results

- `make check`: 52 offline tests pass.
- Kit contract: the `tools` and `security` groups pass (tool result shown with its policy decision; destructive call
  needs approval; identity bound in code). The `sources` and abstention groups still pass.
- Scorer self-test: `make eval-tools-selftest` checks that the scorer catches a wrong tool, a wrong value and an
  over-eager call.
- **Not yet measured:** the model's selection, parameter and over-eager rates. They need a live model:
  `make eval-tools-live`, which needs `OPENROUTER_API_KEY` in `.env` and costs well under 0.02 USD for 20 short cases.

## Lessons

1. **Put the number in the code, not in the answer.** The model writes the sentence; the handler computes the number.
   The test `test_no_tool_result_contains_a_price` and the estimate tests keep it that way.
2. **Make missing data a result, not a guess.** An estimate without an event count returns `needs_input`. The bot then
   asks, which is what the intake harness requires.
3. **Score the scorer.** A metric that cannot fail is not a metric. The self-test gives the scorer three known-wrong
   cases that it must catch.

## Caveats

- The conversation history per thread is not built yet. The kit's thread-isolation test fails until M5 adds it.
- The cost line depends on the model's reported usage. It is only as accurate as the provider's usage figures.
