# M5 lesson: errors, retries, fallback and traces

## Context

A chatbot fails in ways a user should never see as a stack trace: an empty message, a message that is too long, a model
provider that times out in the middle of a tool loop. M5 defines which failures exist, what the user sees for each, and
what the system does before it gives up.

## What was built

- **Typed input errors**: an empty message, a message over 4000 characters, or control characters returns
  `invalid_input: <reason>` before any model call.
- **Bounded retries**: a provider failure is retried twice with a short wait between attempts. The retry count is a
  constant, so the worst case is known.
- **Local fallback**: after the retries, one call goes to a local Ollama model (`qwen3:8b`, configurable). No key, no
  spend. The fallback is used only when the primary has failed.
- **Provider error**: if the fallback also fails (or is absent), the answer is a plain sentence and the error is
  `provider_error: <exception type>`. The exception text is not shown to the user.
- **Per-thread history**: a thread keeps its own turns. Another thread, or another owner, never sees them.
- **One trace line per flow**: each `ask` appends a JSON line with the steps (input check, retrieval, each model call
  with the model that answered, tool calls) and the error. The question text is not written, only its length.

## Results

- `make check`: 64 offline tests pass, including seven error tests.
- Kit contract: all nine groups pass (sources, abstention, tools, security, errors, threads, cost).
- Live fallback check: the local Ollama server is running. A first call to `qwen3:8b` did not return within the time I
  waited (the model may still be loading). The fallback path is tested offline with fake models; a live answer from
  the local model is not yet confirmed.

## Lessons

1. **Decide the failure modes before the success path.** Each typed error is one line in the trace and one test.
2. **Bound every retry.** A retry without a count turns one slow provider into a hung page.
3. **A fallback is a second model you must test.** It needs the same contract as the primary, and it must fail as cleanly.
4. **Trace the decisions, not the text.** The trace records that the input was rejected and which model answered, not the
   owner's words. Logging content would make the trace a privacy risk.
