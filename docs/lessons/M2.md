# M2 lesson: advanced retrieval (query translation and self-query)

## Context

M1 showed that paraphrased questions are where the baseline fails. M2 tries two changes and measures each against the M1
baseline on the same questions, paired by question, so that a change is judged on the difference it makes.

## What was built

- **Query translation** (`translate_keywords`): drops question words and maps the owner's loose words to the area
  vocabulary ("calls" to request terms, "toner" to stock terms).
- **Self-query** (`self_query`): turns a question into metadata filters, `product` and `section`, through a schema.
  A case id such as "C04" maps to the area of that case article. Anything that fails the schema returns no filter.
- **Fallback** (`retrieve`): a missing, invalid or empty filtered result goes to an unfiltered search. Tests cover invalid
  output of several kinds.
- **A/B** (`scripts/eval_advanced.py`): four arms on dev, paired bootstrap intervals, and a replay target.

The offline arms use the lexical embedder, so the A/B needs no key. The live versions (an LLM rewrite and an LLM
self-query) are not built yet; the schema and fallback stay the same when they are.

## Decision rule (fixed before the run)

An arm is adopted when the paired 95% interval of its nDCG@5 difference from the baseline lies entirely above zero.

## Result (dev, 16 answerable questions, offline lexical)

| Arm | nDCG@5 | Difference from baseline [95% CI] | Decision |
|---|---|---|---|
| baseline (M1) | 0.160 | - | - |
| translate | 0.168 | +0.008 [-0.125, 0.137] | rejected |
| self-query filter | 0.270 | +0.110 [0.016, 0.222] | adopted (see caveat) |
| translate + filter | 0.181 | +0.021 [-0.100, 0.139] | rejected |

The filter applied to 6 of 16 questions. Translation on its own did not help, and it made the filter arm worse when
combined with it. The lexical matching behind translation loses the words that carry the meaning.

## Caveat: the adoption is not a held-out claim

The first version of the self-query used area words only and filtered 2 of 16 questions. After seeing that on the dev
questions, I added the case-id mapping (revision 2), because most dev questions name a case. The rule did not change, but
the arm did, after looking at dev. So the adoption above is a dev result, and it must be confirmed on the test split once,
in M7. Until then, report it as "adopted on dev, unconfirmed".

## Lessons

1. **A paired comparison is what makes a change visible.** Unpaired means would have hidden that the filter helped
   precisely the questions it applied to.
2. **Validate before you trust a model's output.** The filter is a dictionary with two enumerated keys. Anything else
   falls back to the baseline, so a bad model output can only cost recall, not add wrong filters.
3. **Changing an arm after seeing dev is a form of tuning.** It is allowed here, but it has to be written down, and the
   result has to be confirmed on data that was not looked at.

## How to read the result

- `make eval-advanced-replay`: recomputes the A/B from the stored per-question nDCG values. Must say "identical".
- `make check`: 44 offline tests, including the fallback tests.
