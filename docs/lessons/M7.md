# M7 lesson: evaluation and limits

## Context

M7 asks the question the earlier milestones could not answer: how far can the numbers be trusted? It has three parts:
the retrieval result on the held-out test split, the tool and attack results, and an honest list of what is not measured.

## What was done

- **The test split was read once**, with `scripts/eval_retrieval.py --split test` and the chosen embedding model. The read is
  appended to `evals/results/test_access.log`, and the script refuses a second read. The replay is `make eval-test-replay`.
- **Not done: the LLM judge.** The judge needs hand labels from the builder, and none were given. So faithfulness and
  relevance are not measured. The retrieval, tool and attack metrics stand on their own.
- **Not done: the M2 A/B on the test split.** The test split was read for retrieval only, so the M2 filter decision is still
  "adopted on dev, unconfirmed". Reading it for the A/B would be a second read, which the rule does not allow.

## Results

| Measure | Dev (16 answerable) | Test (16 answerable), read once |
|---|---|---|
| Recall@5 | 0.812 [0.625, 1.000] | 0.812 [0.563, 1.000] |
| nDCG@5 | 0.682 [0.487, 0.854] | 0.723 [0.518, 0.902] |
| Paraphrase nDCG@5 | 0.571 | 0.675 |
| Identifier nDCG@5 | 0.926 | 0.826 |

Tool selection, live (dev-style fixture, 20 cases): selection 0.55 to 0.60, strict parameters 0.31, lenient 0.56, no
over-eager calls (see M3).

Attacks, live (10 attacks): success rate 0 of 10, destructive 0, false refusals 0 of 5 (see M4).

## Limits, with intervals and causes

1. **Sixteen answerable questions per split.** Every interval is wide. On test, nDCG@5 0.72 has a 95 per cent interval of
   0.52 to 0.90. Differences smaller than about 0.2 between two runs on these questions are not reliable.
2. **Dev and test agree, but only loosely.** Recall is the same, and nDCG is a little higher on test. The test split was read
   after the design was fixed, so this agreement is the better evidence. It is still one split.
3. **The identifier and paraphrase gap runs the other way on test.** On dev, identifier questions score higher. On test, the
   paraphrase type scores higher. With five and eleven questions per type, that reversal is noise, not a finding.
4. **The M2 filter adoption is unconfirmed.** It was adopted on dev after one revision made by looking at dev. The test
   split has not been used for it.
5. **No judge.** Faithfulness and answer quality are not measured at all. An answer can cite the right passage and still
   state something the passage does not say.
6. **Attacks: ten, one model, one run.** A zero says these ten failed. It does not bound the attack success rate for other
   attacks.
7. **Duplicate passages are not measured.** Repeated sentences across articles can crowd the top five. The share of
   duplicate chunks in the top five is not yet a metric, so the effect of repetition is unknown.
8. **The model is not deterministic.** The tool-selection rate moved between runs (0.55 and 0.60), so single runs can
   mislead by a few cases.

## What would surprise a user

The retrieval is good on the questions it was built for and weaker on the reworded ones. A user who asks in a way the
articles do not use will get a passage that is close but not the one that answers the question.

## What I would try next

- Add the duplicate-chunk metric, then the de-duplication and diversity steps described earlier.
- Get about thirty hand labels for faithfulness and relevance, then calibrate the judge on dev before any test use.
- Enlarge both splits, so the intervals are narrower.
- Read the M2 A/B on the test split in a new, separately logged decision, with the label budget in mind.
