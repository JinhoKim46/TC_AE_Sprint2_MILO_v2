# M6 lesson: the chat page

## Context

An answer is only trustworthy if the person can see where it came from and what the system did. M6 puts the sources,
the tool calls and their policy decisions on the same screen as the answer.

## What was built

- **Chat page** (`src/milo/web.py`): the question box, the answer, a progress line while the model works, a cost line
  under each answer, a sources panel (chunk id, document, score, passage start), and a tool-call panel (name, arguments,
  result and policy decision).
- **JSON endpoint** `POST /api/ask`: the same fields as the page, so the page is a thin client.
- **Owner binding**: the owner id is created in the server session. The page cannot send one, and a `user_id` in the
  request body is ignored (a test checks this).
- **Escaping**: every value the page shows is HTML-escaped before it is inserted.

## Manual checklist (to tick in a browser)

- [ ] The page loads and shows the sources, tool-calls and progress areas.
- [ ] A question shows a progress line, then an answer.
- [ ] The sources panel lists the passage the answer came from.
- [ ] A request to record a fact shows a tool call with `allowed`.
- [ ] A request to reset a diagnosis shows `needs_approval` and the answer asks for approval.
- [ ] An empty message shows the typed-error text, not a stack trace.

The screen recording (one answer, one tool call, one blocked action) has to be made in a browser. I have not made it.

## Lessons

1. **Show the decision next to the answer.** A `needs_approval` label tells the person why nothing happened.
2. **Identity comes from the server.** A page that sends its own owner id can be pointed at someone else's data.
3. **Escape everything the model writes.** Model output is text, not markup.

## Checkpoint questions (answer in your own words)

1. Can a user tell, from the screen alone, why the answer says what it says?
2. What does the user see when a tool is blocked?
3. Which manual checklist item would you expect to fail first?
