MILO: a diagnosis chatbot that shows its work

MILO answers questions about how a small service business runs its work. It finds passages in a knowledge base, cites them, uses tools to record facts and to estimate savings as a range, and ends a conversation with a summary and a proposed first spec. Every step is shown. The data is fictional.

How MILO works, end to end

One question goes through five stages. Each stage is recorded in a trace, so the chat can show the path, and the overview can count it.

What the owner sees

  • Landing page with a section index on the right that magnifies under the pointer, and a demo video (36.6 s, with a soundtrack and one keystroke per typed character).
  • Chat: the answer with numbered citations, a confidence line, the steps MILO took (name, arguments, result, policy decision), and a side panel with the sources. Clicking a source opens the full document with the passage highlighted in its context.
  • Summary and proposed spec at the end of a conversation: what was recorded, the estimate per area as a range with its assumptions, what is still missing, and the first area to start with. It is computed in code and calls no model.
  • Accounts: sign-up, sign-in (back to the landing page), password change, and an owner account that sees the overview: every account and every question, the tool use, the system status and the spend against the course cap.
  • History is stored with each turn, including the tool calls, so a reloaded conversation shows the same steps as the live one (migration 0004).

Labels and the judge

  • LLM judge: not usable. Agreement with the labels was 0.83 with kappa 0.60 and a lower bound of 0.29, below the rule (kappa at least 0.60 and lower bound at least 0.30). The labels came from a model, not from a human.
  • Question labels, batch 1 (35 answerable questions): all 35 were labeled 1 by both labelers. Agreement 100%, but kappa is undefined because there were no negatives.
  • Question labels, batch 2 (20 items: 15 negatives, 5 positives): both labelers agreed on all 20, kappa 1.0. The negatives are unrelated sentences from the same folder, so they are easy. This does not show reliability on hard negatives.
  • Guidelines are in evals/labeling/GUIDELINES.md. The rule for accepting a label set is fixed in advance: kappa at least 0.60 and a lower bound at least 0.30. If it fails, the guidelines change, not the numbers.

Chat engine, tools and experiments since the last report

  • Chat engine. Live answers run on LangChain's create_agent (LangChain 1.x, model anthropic/claude-haiku-5.5 on OpenRouter). The agent decides when to search and which tools to call; the six tools and their rules are the same. Without a live key, or if the agent fails, the app's own loop runs with its retries and the local model.
  • Same cases, two engines (20 tool cases, one live run each, same scorer): the app's loop gave selection 0.65, strict parameters 0.25, lenient 0.56, false calls 0. create_agent gave selection 0.80, strict 0.44, lenient 0.69, false calls 0.25 (it searched four times for a greeting-type question). Destructive calls were paused for approval by the agent's middleware. One run of 20 cases shows the direction only.
  • Hybrid search (BM25 with the embeddings, fused by reciprocal rank) was tested on a fresh held-out set of 40 items, read once (32 answerable). Hybrid minus dense nDCG@5: -0.03, 95% interval [-0.16, 0.07]. The interval contains 0, so the rule gives no decision and hybrid is not adopted. This is the result on this set; it is not a claim that hybrid is worse in general. An earlier draft of this report said hybrid had been tested in the earlier project; no such result exists in this repository.
  • Tools as an MCP server. src/milo/mcp_server.py serves the six tools over MCP (streamable HTTP, MCP 1.x). Identity comes from the bearer token, never from an argument. reset_diagnosis runs only with an approval recorded on the server. Tested in memory (four tests); not yet run over real HTTP. Other MCP clients can call these tools; end users still use the web chat.
  • Automated screen recording. docs/video/demo-recording/ holds a browser-automated recording of one session with the live model: a question, tool steps, the full-source viewer, a fact recorded by a tool call, a blocked action waiting for approval, and the summary. It is made by a script, not by a person at a screen, and the README says so.
  • Narration. The recording is narrated with Piper, a local voice that runs offline, using the public-domain LJSpeech model (the Lessac model was dropped because its data is research-licensed). A calm delivery, and a quiet background under the speech. The final file is narration only; subtitles are available as an option and are off by default.

Limits, stated plainly

  • Answerable questions per split are few (16 on test). Every interval is wide. Differences under about 0.2 nDCG are not reliable.
  • The M2 self-query filter was chosen on dev after one revision. The test split was read once already (the Gemini baseline), so the filter cannot be confirmed on test without a second read. This needs an owner decision.
  • The tool-description change was measured on the same 20 cases it was tuned on. It is not yet shown on fresh cases. Strict parameter accuracy did not change (0.31).
  • Labels are written or checked by models, not humans. Two labelers agreed, but the batch 2 negatives are easy, and the batch 1 set has no negatives.
  • The 40 extra dev questions were written by a model from the knowledge base. Their quotes were checked verbatim. The question wording and the unanswerable items were not checked for overlap with the knowledge base beyond that.
  • Ten attacks and one model. A zero says these attacks failed, not that the system is secure.
  • The database connection uses the admin role. A limited role is needed before any real data.
  • The overview, the summary and the tool steps were checked in a browser, and a real-time screen recording of one session is in docs/video/demo-recording/. The M6 checklist is ticked in docs/lessons/M6.md, with the one open item (empty message) re-checked after its fix.

Demo storylines for the evaluation

Four scripted conversations are in data/demo_storylines.json and are served at /api/demo. Each shows a different part of the system.

  • The same printer, two technicians. A duplicate-dispatch story: sources, a savings estimate with a range, and a fact recorded from the owner's words.
  • We have toner, but nobody can find it. The consumables area, with the calculation done in code.
  • When MILO should not answer. A question the knowledge base cannot answer. MILO says what is not established, and the confidence line shows a weak match.
  • A change that needs your approval. The destructive tool is refused until approval, and the card shows why.

Reproduce the results

  • Checks: make check (lint, format, 93 offline tests); make contract (kit contract, 9 groups).
  • Replays with no model call: make eval-retrieval-replay, make eval-test-replay, make eval-advanced-replay.
  • Run the app: MILO_LIVE=1 MILO_STORE=postgres uv run python -m milo.serve, then open / for the landing page and the chat, and /dashboard for the overview (owner account only).
